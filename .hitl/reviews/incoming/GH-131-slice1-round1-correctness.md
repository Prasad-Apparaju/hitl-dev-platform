## Findings

**D1 (decide, check 10). The CI template's regression guard cannot fire on the common path.** `ci/workflows/data-layer-check.yml:33` diffs the PR's files against the PR's own `docs/02-design/data/scorecard.yaml`. The skill's Validate stage (SKILL.md:189) copies the old scorecard to `.hitl/data-layer/previous/` and then rewrites `scorecard.yaml`, so a PR produced by the skill always commits a baseline equal to its result. CI then catches only hand edits to the four files made after the last scorecard write; a regression the run itself produced is reported locally and never in CI. Evidence: on the untouched fixture `--baseline docs/02-design/data/scorecard.yaml --strict` exits 0; after setting lin:1 to needs-review it exits 1 with "verification_rate.edges went from 0.25 to 0.0" listed first. Smallest fix, if CI is meant to be a guard and not a mirror of the local run: baseline against the base branch (`git show origin/$GITHUB_BASE_REF:docs/02-design/data/scorecard.yaml > /tmp/base.yaml`, skip when absent). If the local run is the intended guard (LLD §5, ADR text at 02-adrs.md:222), say so in the template's header comment.

**M1 (minor, check 10). An empty `data_layer:` key in `.hitl/config.yaml` fails the CI step in both modes.** `data-layer-check.yml:29` does `.get('data_layer',{}).get(...)`; YAML gives `None` for an empty key, and the lookup raises AttributeError (reproduced: `printf 'data_layer:\n'` then the one-liner exits 1). Under GitHub's `bash -e` the step fails before the validator runs. Fix: `((d or {}).get('data_layer') or {}).get('blocking', False)`.

**M2 (minor, check 7). The live write-method guard is an `assert` over five names.** `tools/data-layer/profile_adapter.py:251` refuses a fetch with insert/update/delete/write/execute by `assert`, which `python3 -O` strips, and which leaves no run.log line. The protocol itself is clean (`ReadOnlyFetch`, lines 29 to 36: stores, count, sample only). Fix: an explicit `if` that logs `result=refused reason=write_method` and exits 2, and include `save`, `put`, `remove`, `drop` in the name list, or check `set(dir(fetch)) - {stores, count, sample}` for callables.

**M3 (minor, check 12). Two test-plan promises have no test.** FIX-3 (every template under `ai/shared/templates/data-layer/` parses and carries only keys the schema lists) has no test; the nearest is `test_shipped_schema_is_the_template`, which compares the two schema copies. LINT-1's second half (every `shared/` path the skill names exists in the built plugin) is checked against the source tree only (`ci/wiring/test_wiring.py:883-895`); I verified the built plugin by hand (three `$ROOT/shared/...` paths, all present). Fix: one parametrized test over the seven templates against the schema's key lists; the built-plugin check belongs in build.sh or the release checklist.

**M4 (minor, check 2). The scan's `declared_from` lines differ from the fixture's hand-written ones.** intake_scan proposes `docker-compose.yml:4` and `:8` (the `image:` lines) where sources.yaml says `:3` and `:7` (the service-name lines). Harmless, since the person edits the proposal, but the fixture is not what the scan produces. Fix: either point the scan at the service-name line or regenerate the fixture rows from the scan.
